# Phase 4: Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sync all synced tables between a user's devices through one snapshot per sync code (`snapshots/<sha256(secret)>.json`) in a Vercel Blob private store, with per-record last-write-wins merge, ETag concurrency, sync UI, duplicate-friend merge and tombstone cleanup.

**Architecture:** Pure `merge`/`purgeTombstones`/integrity functions in `src/domain/sync/`. A Vercel Function `api/snapshot.ts` (GET/PUT) maps the bearer secret to that user's blob and guards writes with ETags; its logic lives in `api/_handler.ts` behind a `SnapshotStore` interface so tests use an in-memory store. On the client, `src/data/sync/SyncService.ts` runs fetch → merge (inside one Dexie rw transaction) → conditional upload, with a mutex and up to 3 attempts; `triggers.ts` fires it on start, foreground, `online`, and 5 s after the last local write. `SyncService` joins `Repositories` so viewmodels and tests inject it like any repository.

**Tech Stack:** React 19, TypeScript, Dexie 4 (`liveQuery`), zod 4, `@vercel/blob` 2.8.x, Vercel Functions (Web `Request`/`Response`, Node runtime), Vitest + fake-indexeddb + fast-check, Playwright.

**Spec:** `docs/SPEC.md` section 9 (and 4, 8, 12 Phase 4, 13 items 9–10)

## Global Constraints

- IndexedDB stays the working source. No screen waits on the network; sync failure only changes status.
- One blob per sync code: pathname `snapshots/<sha256 hex of secret>.json`, `access: 'private'`. `BLOB_READ_WRITE_TOKEN` exists only on the server. The secret itself is never stored server-side and never logged; snapshot content is never logged. No `SYNC_SECRET` env.
- Secret = 32 random bytes from `crypto.getRandomValues`, base64url without padding (43 chars), generated on the client. Server accepts only `^[A-Za-z0-9_-]{43}$`; missing or malformed → `401`.
- PUT body: validated with the existing `snapshotSchema` (`src/domain/snapshot.ts`), size < 5 MB (`413` otherwise), `schemaVersion > SCHEMA_VERSION` → `400`.
- Merge per table by `id`: one side only → keep; else larger `updatedAt`; tie → the one with `deletedAt`; tie → larger `JSON.stringify` (lexicographic). Commutative, idempotent, never drops an id.
- Tombstones with `deletedAt` older than **180 days** are hard-deleted locally and dropped from the uploaded snapshot.
- Sync attempts: at most **3** per run; `412` → retry from GET. Debounce after local write: **5 s**.
- Meta keys (device-local, never synced): `syncSecret`, `lastSyncAt`, `remoteEtag`, `syncedUpTo`.
- No Dexie version bump; `SCHEMA_VERSION` stays `1`.
- Every new string in both `src/i18n/locales/vi.ts` and `en.ts`. Touch targets ≥ 44px. Layer rules in `eslint.config.js` keep passing (views never import `@/data`, Dexie, or `@/domain/*` besides types).
- Only new dependency: `@vercel/blob@^2.8.2`.

## Review Focus

1. A local edit lands while a sync is between "read local" and "write merged". The edit must survive (not be overwritten by the older merged copy) and be pushed by a later sync. Test in Task 4.
2. `sync()` called while a sync is running (debounce + `visibilitychange` together). Must not run two in parallel, and a write made during the run must still be uploaded afterwards. Test in Task 4.
3. Remote snapshot has `schemaVersion` 2 (other device updated first). Must not merge or upload; status error `newerSchema`. Test in Task 4.
4. Same transaction has a debt for both duplicate "Nam"s; merging them must not leave two live debts for one friend on one transaction (the edit form would then reject it with `duplicateSplitFriend`), and balances must be unchanged. Test in Task 6.
5. Mistyped code pasted on a new device (valid format, no blob). Must not silently create a new empty store: `joinWithSecret` fails with `syncCodeNotFound`, secret not saved, local data unchanged. Test in Task 4.
